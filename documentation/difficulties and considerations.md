# Cloud Difficulties and Security Considerations Encountered
-	Throughout the configuration and testing of my AWS environment I encountered difficulties with certain services and billing.
-	During the creation of the MFAFalseDenyAll policy, I learned that it is not efficient to simply deny access to every single AWS resource if MFA is not enabled on a given account for my use case. This is because the account is essentially deadlocked without the help of the root user. I found myself running back and forth between my admin and root user accounts to enable MFA manually. I decided to tweak the policy to enable necessary access to certain services (such as the ability to enable MFA) for accounts lacking MFA. In very restricted and secure production environments I can see how a broad deny all can be a viable solution, but in my use case, it saves more time to allow the restricted account to remediate its own lack of MFA without sacrificing security.
-	The decision to place my EC2 server in a public subnet was made considering the high cost of a NAT gateway (to enable private servers to communicate with the internet securely) and the use-case for my lab.
-	I originally attached an overprivileged admin role to my EC2 instance without realizing the potential blast radius on my AWS account caused by an infiltrated server.
-	Enabling SSM (Systems Manager) for secure, IAM based authentication into my EC2 instance took multiple steps. Even after creating an instance role with SSM policies enabled, the SSM connection status for my EC2 instance was still showing up as not connected. I sharpened my networking skills by troubleshooting this problem.
o	All of the standard boxes were checked: public subnet with internet gateway route, EC2 security groups allowed for outbound HTTPS (TCP 443), NACL allows inbound on ephemeral return ports, DHMC enabled, autoassign public IP enabled, EC2 role has ssmmanagedinstancecore.
o	The problem was that I had originally launched this EC2 instance without a public IP address. On launch, AWS typically attaches a public IP address to the EC2 instance’s Elastic Network Interface (ENI). Since I launched without a public IP address, there is no way to retroactively inject a public IP address.
o	From here, I have a few options: tear down and start up another instance with public IP enabled, use an elastic IP which persists and operates at an internet gateway rather than the ENI level, or create 3 core VPC endpoints that can reach necessary SSM services. For granularity and security, I chose the last option.
	This means that my instance will not have an assigned public IP address until I assign an elastic IP or launch an instance with the proper settings.
o	Even with all of the above enabled and configured, I still ran into problems enabling SSM. After an hour of troubleshooting with Amazon Q, I found out that my Security Group had not allowed inbound HTTPS. This fixed the problem.
